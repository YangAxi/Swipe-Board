# Feature Specification: Swipe Board MVP

**Feature Branch**: none — local kickoff

**Created**: 2026-11-09

**Status**: Phase 1 implemented (T001–T011); US2 / US3 pending

**Input**: 用户原始要求

> 我想打造一个面向 UCLA 校园及周边用户的 Meal Swipe 供需信息平台。持有闲置 swipes 的用户可以发布出售信息，有需求的用户可以浏览、筛选和发布求购信息。平台通过统一展示价格、数量、日期、时间、餐厅和交接方式，减少分散在微信群及小红书中的重复询问，并支持沟通、双方确认和交易记录。

此前完整基准保存为 input-baseline.md。该文件是讨论证据，本规格为当前功能的需求入口。

## User Scenarios & Testing

### User Story 1 - 查看并发布供需 (Priority: P1)

游客查看有效供需帖子，校园账户发布出单或收单，其他账户发布收单。

**Why this priority**: 清楚列出需求是用户明确指定的核心价值。

**Independent Test**: 发布一条未来有效出单，在首页按地点和价格找到它，刷新后仍存在。

**Acceptance Scenarios**:

1. **Given** 有不同地点和时间的帖子，**When** 用户筛选今天或明天、餐厅和价格，**Then** 只看到所有条件都符合的有效帖子，空结果可清除条件。
2. **Given** 校园账户，**When** 填写单价、数量、日期、时段、餐厅、用餐与交接方式，**Then** 有效帖子可发布并在本人列表管理。
3. **Given** 普通邮箱账户或游客，**When** 尝试发布出单，**Then** 操作被拒绝。游客需先登录才能发布收单。
4. **Given** 本人帖子，**When** 暂停或关闭，**Then** 不再接受新交易，既有记录仍可查看。

### User Story 2 - 联系与双方确认 (Priority: P2)

用户从帖子直接联系对方，商定数量和单价后双方确认。

**Why this priority**: 减少重复询问，并让余量可以信任。

**Independent Test**: 两位演示用户针对一条帖子交换消息并分别确认，观察预留数量变化。

**Acceptance Scenarios**:

1. **Given** 用户进入他人的帖子，**When** 点击联系，**Then** 复用该帖子与双方的对话，消息关联清楚，库存不变。
2. **Given** 一笔提案，**When** 双方确认同一版本的条款且余量足够，**Then** 对应数量预留。修改条款使旧确认失效。
3. **Given** 最后一个余量和两笔提案，**When** 依次确认，**Then** 仅一笔可成功预留，重复点击不重复扣减。
4. **Given** 收单，**When** 普通邮箱用户尝试以卖方身份响应，**Then** 被拒绝。

### User Story 3 - 完成、取消与反馈 (Priority: P3)

双方完成交易确认，查看历史并反馈问题。

**Why this priority**: 让数量、个人记录和信誉有可追踪依据。

**Independent Test**: 单方确认完成时不计完成数，双方确认后只计一次，完成者可各评价一次。

**Acceptance Scenarios**:

1. **Given** 已预留交易，**When** 双方确认完成，**Then** 预留转完成，记录保留。
2. **Given** 已预留交易，**When** 一方申请取消且另一方同意，**Then** 释放一次库存。
3. **Given** 交易争议或时间已结束，**When** 检查记录，**Then** 未解决的预留不会自动重新出售，提案可过期。
4. **Given** 完成交易，**When** 每位参与者提交一次评价，**Then** 显示评价数量，私密举报只可由提交者和运营处理流程访问。
5. **Given** 用户屏蔽对方，**When** 对方发起新联系或交易，**Then** 被阻止，既有记录仍能解决。

### Edge Cases

- 禁止自我交易和查看无关私密对话，邮箱不进入公开资料。
- 校园邮箱精确允许 ucla.edu 和 g.ucla.edu。身份模拟必须明显标注。
- 数量为正整数，价格非负，预算上下限有序，时段同日且未结束。
- 价格以每次 swipe 显示，最终条款同时显示总价。
- 有预留时不能修改实质条件，数量不能低于预留与已完成之和。
- 存储失败、无结果、帖子关闭、过期、数量不足都有可理解反馈。
- 加载损坏的演示数据不得静默覆盖，允许用户主动重置。

## Requirements

### Functional Requirements

- **FR-001**: 两个供需标签，默认今天和明天，可查看全部未来帖子。
- **FR-002**: 同时按日期、时间重叠、餐厅、方式和价格筛选，支持相关价格排序与最新排序。
- **FR-003**: 字段包括类型、日期、时段、地点、数量、单价或预算、用餐方式、交接方式、备注。
- **FR-004**: 校园与普通邮箱权限依上述故事执行，个人邮箱私密。
- **FR-005**: 本人可编辑、暂停、重新开放和关闭，已预留交易不受关闭影响。
- **FR-006**: 对话直接从帖子发起，同一帖子同一用户对复用对话。
- **FR-007**: 双方确认一致条款才预留，重复操作幂等，取消和完成维持数量守恒。
- **FR-008**: 支持历史、完成后评价、私密举报及屏蔽。
- **FR-009**: 修改和消息刷新后保留，首次示例数据不覆盖操作。
- **FR-010**: 清楚区分演示身份与真实验证，所有交易为模拟，不制造学校许可或安全保证。
- **FR-011**: 使用洛杉矶日期和时间，价格使用美元，交接方式与下单方式分开。
- **FR-012**: 界面支持手机与桌面、键盘操作、可见标签及空态错误态。

### Key Entities

账户、供需帖子、对话、消息、交易、评价、举报和屏蔽关系。
交易关联一个源帖子，明确买卖双方，帖子同时维护总量、预留和完成量。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 测试者可在 30 秒内找到指定条件的帖子，目标由首次用户测试验证。
- **SC-002**: 测试者可在 60 秒内发布完整帖子，目标由首次用户测试验证。
- **SC-003**: 发布、联系、双方确认、完成四步可完整演示，刷新后数据保留。
- **SC-004**: 两个用户争取最后一个余量和重复确认场景均不出现负库存或重复完成。
- **SC-005**: 390px 手机宽度与桌面均无水平溢出，主要任务均可操作。
- **SC-006**: 权限拒绝、自我交易、过期和无结果四类异常均有明确提示。

## Assumptions

- 沿用已接受基准，第一版为英文、移动端优先、单浏览器多人角色模拟。
- 模拟邮箱和消息不能支持实际校园验证、跨设备通信或多人并发。
- 真实上线的认证、支付、数据基础设施及校规运营问题后续单独处理。
- 暂名 Swipe Board。社交匹配和兴趣推荐不进入第一版。
